# Отчет: Узкие места при миграции системы "Медикаменте"

## Введение

В рамках миграции от монолитной файл-ориентированной системы (Excel + 1С) к современной микросервисной архитектуре выявлены потенциальные узкие места, которые могут негативно повлиять на успешность проекта.

## Методология

Использована диаграмма Исикавы (Fishbone Diagram) для систематического анализа причинно-следственных связей. Проблемы сгруппированы по 6 категориям.

## Выявленные узкие места

### 1. Инфраструктура

#### Проблемы

**1.1. Низкая производительность старых серверов**
- Windows Server 2022 на устаревшем железе
- Недостаточно ресурсов для параллельного запуска старой и новой систем

**1.2. Недостаток RAM для параллельной работы (Parallel Run)**
- Текущие серверы: вероятно 16-32 GB
- Требуется: минимум 64 GB для одновременной работы систем

**1.3. Медленная сеть (Gigabit)**
- Синхронизация больших объемов данных (25 лет медкарт) займет значительное время
- Недостаточная пропускная способность для real-time синхронизации

**1.4. Отсутствие Kubernetes кластера**
- Нет опыта развертывания микросервисов
- Требуется закупка или аренда инфраструктуры

#### Меры устранения

| Мера | Приоритет | Срок | Стоимость |
|------|-----------|------|-----------|
| Upgrade серверов (CPU + RAM до 128 GB) | ВЫСОКИЙ | 2 недели | 500 000 руб |
| Upgrade сети до 10 Gigabit или волокно | СРЕДНИЙ | 1 месяц | 200 000 руб |
| Аренда k8s в облаке (Yandex Cloud) на период миграции | ВЫСОКИЙ | Немедленно | 50 000 руб/мес |
| Подготовка тестовой среды на отдельном сервере | ВЫСОКИЙ | 1 неделя | 200 000 руб |

### 2. Программное обеспечение

#### Проблемы

**2.1. Excel → PostgreSQL: миграция структуры данных**
- Excel не имеет фиксированной схемы
- Различные форматы в разных файлах
- Необходима очистка и нормализация данных

**2.2. 1С в файловом режиме: блокировки**
- При работе с файлом базы возможны блокировки
- Сложность экспорта данных при активных пользователях
- Требуется downtime

**2.3. Несовместимость версий**
- Новая система: Java 17, PostgreSQL 15, современный стек
- Старая система: 1С может быть на старых версиях
- Риск проблем при интеграции

**2.4. Отсутствие API в старых системах**
- 1С работает через OLE, нет REST API
- Excel - ручной экспорт
- Файловый сервер - нет программного доступа к метаданным

#### Меры устранения

| Мера | Приоритет | Срок | Ответственный |
|------|-----------|------|---------------|
| Разработка ETL pipeline (Apache NiFi) для миграции Excel | КРИТИЧЕСКИЙ | 1 месяц | Data Engineer |
| Миграция 1С в клиент-серверный режим до начала переноса | ВЫСОКИЙ | 2 недели | 1С специалист |
| Создание адаптеров для интеграции со старыми системами | ВЫСОКИЙ | 3 недели | Backend разработчик |
| Data Quality проверки и cleanup скриптов | СРЕДНИЙ | 2 недели | Data Engineer |

### 3. Интеграция

#### Проблемы

**3.1. Синхронизация данных при Parallel Run**
- Необходимость двусторонней синхронизации между старой и новой системами
- Риск data inconsistency
- Конфликты при одновременном изменении

**3.2. Рассинхронизация**
- Данные в Excel обновляются вручную
- 1С автоматически
- Новая система в реальном времени
- Источник истины неясен

**3.3. Интеграция с внешней лабораторией**
- Канал передачи данных не определен в As-Is
- Лаборатория может не поддерживать API
- Требуется согласование формата данных

**3.4. ККМ → 1С OLE: legacy интеграция**
- Старая технология OLE
- При переходе на новую систему нужна перенастройка ККМ
- Риск нарушения фискальной отчетности

#### Меры устранения

| Мера | Приоритет | Срок | Ответственный |
|------|-----------|------|---------------|
| Определить систему-источник истины (Master Data Management) | КРИТИЧЕСКИЙ | До начала | Архитектор |
| Разработка синхронизационного слоя (Change Data Capture) | КРИТИЧЕСКИЙ | 1 месяц | Backend team |
| Согласование API с лабораторией, тестовые интеграции | ВЫСОКИЙ | 2 недели | Интеграционный специалист |
| Переключение ККМ на новую систему в тестовом режиме | СРЕДНИЙ | 1 неделя | 1С + Java разработчик |
| Freeze изменений в Excel за неделю до cutover | КРИТИЧЕСКИЙ | По плану | Project Manager |

### 4. Персонал

#### Проблемы

**4.1. Недостаток компетенций**
- IT-отдел (3 человека) не имеет опыта с микросервисами
- Нет экспертизы в Kubernetes, Docker, Java Spring Boot
- Отсутствие DevOps культуры

**4.2. Сопротивление изменениям**
- Сотрудники привыкли к Excel
- Ресепшен не хочет учить новую систему
- Врачи боятся сложности

**4.3. Недостаточное обучение**
- Нет программы обучения
- Недостаточно времени на освоение
- Отсутствие документации

**4.4. Нехватка IT-специалистов**
- 3 человека на всю компанию
- Не хватает для миграции и поддержки старой системы одновременно
- Риск burnout

#### Меры устранения

| Мера | Приоритет | Срок | Стоимость |
|------|-----------|------|-----------|
| Привлечение внешних консультантов (архитектор, DevOps) | КРИТИЧЕСКИЙ | На период миграции | 500 000 руб/мес |
| Обучение IT-команды (курсы по k8s, микросервисам) | ВЫСОКИЙ | 1 месяц до начала | 150 000 руб |
| Программа обучения для сотрудников (ресепшен, врачи) | ВЫСОКИЙ | 2 недели до cutover | 100 000 руб |
| Найм временных специалистов (2-3 человека) | СРЕДНИЙ | На 6 месяцев | 300 000 руб/мес |
| Change Management программа (коммуникация, мотивация) | СРЕДНИЙ | Весь период | 50 000 руб |

### 5. Процессы

#### Проблемы

**5.1. Отсутствие процедуры отката (Rollback Plan)**
- Нет плана действий при провале миграции
- Непонятно, как вернуться к старой системе
- Риск потери данных при откате

**5.2. Нет тестовой среды**
- Тестирование на production недопустимо
- Невозможно проверить миграцию заранее
- Высокий риск ошибок в cutover день

**5.3. Downtime для пациентов**
- Запись на прием будет недоступна во время cutover
- Пациенты не смогут просматривать результаты
- Риск репутационных потерь

**5.4. Двойная запись (Excel + 1С)**
- Кассиры вручную дублируют данные
- При миграции нужно учесть обе системы
- Риск расхождений

#### Меры устранения

| Мера | Приоритет | Срок | Ответственный |
|------|-----------|------|---------------|
| Разработка детального Cutover плана с rollback процедурой | КРИТИЧЕСКИЙ | 2 недели до cutover | Project Manager |
| Создание тестовой среды (копия production) | КРИТИЧЕСКИЙ | 1 месяц до начала | DevOps |
| Планирование cutover на выходные/ночь | ВЫСОКИЙ | В плане | PM |
| Резервное копирование всех систем перед cutover | КРИТИЧЕСКИЙ | За день до cutover | IT-администратор |
| Устранение двойной записи ДО миграции (автоматизация) | СРЕДНИЙ | 1 месяц | Backend разработчик |

### 6. Данные

#### Проблемы

**6.1. Качество данных в Excel**
- Дубликаты пациентов (разные написания ФИО)
- Ошибки ввода
- Неполные данные
- Разные форматы дат

**6.2. Большой объем данных**
- 25 лет истории медкарт (требование законодательства)
- Тысячи сканов документов
- Сотни гигабайт файлов
- Миграция займет много времени

**6.3. Отсутствие стандартизации**
- Каждый врач ведет журнал по-своему
- Папки пациентов имеют разную структуру
- Файлы в разных форматах (PDF, JPG, DOCX)

**6.4. Миграция сканов**
- Нет OCR - невозможно извлечь текст
- Нет метаданных - непонятно, что в файле
- Нет привязки к конкретным визитам

#### Меры устранения

| Мера | Приоритет | Срок | Ответственный |
|------|-----------|------|---------------|
| Data Quality audit и cleanup (dedupe, validation) | КРИТИЧЕСКИЙ | 1 месяц | Data Engineer |
| Поэтапная миграция данных (последние 3 года сначала) | ВЫСОКИЙ | В плане миграции | PM + Data Engineer |
| Стандартизация структуры данных перед миграцией | ВЫСОКИЙ | 2 недели | Бизнес-аналитик |
| OCR для сканов (опционально, для новой системы) | НИЗКИЙ | После миграции | Data Scientist |
| Миграция файлов в фоне (не блокирует cutover) | СРЕДНИЙ | 1-2 месяца после | DevOps |

## Рекомендуемая стратегия миграции

### Выбор: Parallel Run

**Обоснование:**
- Минимизация рисков (можно откатиться)
- Постепенный перевод пользователей
- Время на устранение ошибок

**Этапы:**

1. **Подготовка (месяц 1-2)**
   - Upgrade инфраструктуры
   - Data Quality cleanup
   - Обучение команды

2. **Разработка интеграции (месяц 2-3)**
   - ETL pipeline
   - Синхронизационный слой
   - Тестовая среда

3. **Pilot (месяц 4)**
   - 2-3 врача на новой системе
   - Синхронизация с основной
   - Сбор feedback

4. **Parallel Run (месяц 5-6)**
   - Все врачи работают параллельно
   - Постепенное отключение Excel
   - Мониторинг качества данных

5. **Cutover (конец месяца 6)**
   - Отключение старой системы
   - Freeze данных в Excel
   - Миграция архивных данных в фоне

## Выводы

1. Наиболее критичные узкие места: **качество данных**, **отсутствие процедур отката**, **недостаток компетенций**.

2. Рекомендуемая стратегия: **Parallel Run** для минимизации рисков.

3. Необходимо привлечение внешних специалистов для успешной миграции.

4. Ключевой фактор успеха: детальное планирование и тестирование.

5. Бюджет: ~7.5 млн руб на устранение узких мест и успешную миграцию.
